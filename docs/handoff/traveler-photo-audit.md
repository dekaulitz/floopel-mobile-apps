# Traveler profile photo and banner picker

8 November 2026. Scope: the disabled **Ubah foto** action, the two-step existing Trip banner picker, the Community own-publication clone error, and the reported Location Open Trip horizontal padding. Changes stay on `feature/mobile-openapi-contracts` (PR #1).

## Photo journey

The existing profile-photo repository/HTTP adapter was not connected to the runtime or editor. Android now supplies its Activity-owned `PickVisualMedia` launcher and bounded native cropper; shared Compose uses a retained photo ViewModel and domain contracts. The editor remains mounted beneath the photo dialog. Avatar-only profile refreshes preserve its unsaved metadata fields.

The user chooses a JPEG/PNG/WebP, adjusts a square crop, zooms/pans/rotates, then explicitly chooses **Selesai** before one upload. Cancel sends nothing. Raw input is bounded at 32 MiB; decoding is sampled to a maximum side of 2048 and export to a maximum square side of 1024. Encoded upload remains at most 5 MiB. Input/output byte arrays are defensive copies. Paths and image bytes stay out of navigation, journals and logs. The native picker requires no broad gallery permission or persisted URI grant; see the [official picker documentation](https://developer.android.com/training/data-storage/shared/photo-picker) and [bounded bitmap decoding options](https://developer.android.com/reference/android/graphics/BitmapFactory.Options).

Existing consent preflight runs immediately before POST; failure preserves the crop, and returning from Legal never posts automatically. A 202 response means PROCESSING, with the old avatar retained. Foreground polling reads the accepted request ID every two seconds, at most fifteen times; closing/backgrounding stops those reads. Completion requires the matching READY request and a fresh canonical owner profile with an avatar. Failed status reads retain a manual read path. Unknown POST results have no replay and no invented request ID/success; a status check without an ID only reads the current profile. Selection and upload results from another identity generation are discarded. This journey is in memory; process death loses the pending photo ID/crop and reopens through a canonical profile read.

API paths remain POST `/me/profile-photo-uploads` and GET `/me/profile-photo-uploads/{upload_id}`. No idempotency header, new endpoint, retry contract, backend policy or credential is introduced. HTTP success, processing and account mutation are not inferred from opening a picker.

The Android adapter uses AndroidX ExifInterface **1.4.2** for legacy API 24–27 orientation, declared explicitly in the version catalog. This version was already resolved transitively through Coil; the declaration makes the native dependency direct. Its [official stable release notes](https://developer.android.com/jetpack/androidx/releases/exifinterface#1.4.2) were checked. Existing Compose UI is also a direct app dependency for the native dialog window provider. No toolchain version changes.

## Publication, Trip entry and padding

The reported Community 409 was a local fixture account attempting to clone its own publication. The UI hides Copy when ownership is known, and the ViewModel checks ownership before clone; an unavailable profile is read before deciding. An own-publication error has specific user copy. Error refresh performs reads and only dismisses definite feedback when no mutation recovery is required; it does not replay a mutation or release a durable recovery record. Existing records are not cleared or rotated to conceal the original failure.

The purple/yellow cover and “Android QA…” title in the user's public-profile screenshot are existing database fixture content. They are not a new design asset. The card represents a published itinerary. **Profile → Itinerary saya → owned itinerary → Buat Trip dari itinerary** opens Trip creation with the first Spot's timezone; empty plans cannot create a Trip. An explicit complete fixture form creates one synthetic Trip. No user Trip is created during this audit.

Figma Location section [53:1225](https://www.figma.com/design/ifQcOxbjGTXw9aNH2JGl9g/Floopel-Mobile?node-id=53-1225) already matches the production row: 16 dp outer gutters, 76 × 80 dp image and 12 dp image/text gap, without extra inner horizontal padding. Native checks cover one long title and three long rows at 130% text. No speculative padding is added.
