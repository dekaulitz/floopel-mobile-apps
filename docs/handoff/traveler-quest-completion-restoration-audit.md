# Completed Quest restoration through Passport

8 November 2026. Follow-up to `4b54437`, scoped to **QUEST-COMPLETION-RESTORE-01** on PR #1's `feature/mobile-openapi-contracts`. The original report was a source finding, with no original native or live API reproduction.

A completed owner participation can remain in the saved stack beneath Passport while a new Session has no participation or owner projection. Passport's active list excludes that completed participation; recent completions identify receipts, not participation read intents. The old continuation admission gate therefore returned before requesting the saved participation, leaving a generic progress screen without completion or the Passport action.

`continuePassportQuest` now performs the existing authorized GET for that read intent independently of the active cache. Existing resource-ID validation, session generation, read sequencing, cancellation and bounded authentication retry remain responsible for the request. The response must match the requested participation ID before it can populate state. Backend authorization remains authoritative: a serialized ID grants no ownership, and denied/missing/invalid responses cannot populate a completion. The taken-list entry retains its existing cache-based selection admission and return destination.

No answer, GPS proof, admission or reward claim is replayed. There is no new endpoint, persistent credential, journal change, reward/policy change, provider configuration or new production UI. [Figma 220:3251](https://www.figma.com/design/ifQcOxbjGTXw9aNH2JGl9g/Floopel-Mobile?node-id=220-3251) was inspected only for completed Quest/Passport context.
