## QUEST-GROUP-RECOVERY-01

Finding key: `quest-group-create-read-reconcile-recovery-20261108-0327`.

The actual adapter with mock HTTP reproduces create A accepted with its response lost. Authorized GET then shows the active group, but a different invite B remains blocked locally by A's journal before its POST. The old UI hid Create once the group appeared, and its create preflight could return an existing group without acknowledging the frozen command. Refresh/Back did not finish that recovery. This concerns a journaled group command for the same actor; it is not a permanent/all-app/individual-Quest lock or a reproduction on a real account.

The state owner now exposes the Figma “Hasil belum dapat dipastikan” → “Periksa status” → “Memeriksa kelompok” interaction. Back preserves the record and leaves a reachable status action on the group screens. A restored recovery route still requires an authorized review. Create retries reach the adapter rather than returning a preflight-only success; a legitimate same-command retry uses the original stored key and receipt.

Review performs GETs of the actor's current groups and recipient invitations, plus sent invitations for groups they currently manage. It follows the existing pagination instead of treating page one as complete. These are current authorized roles/counts/statuses, not a mutation receipt. The journal grants a local review ticket only when the actor, identity generation and exact stored record agree before and after the read. “Mulai tindakan baru” is a separate explicit decision that releases only that unchanged record. No command, replay or key rotation occurs during GET/review/release. A different action is still chosen by the user afterwards. Failed/stale/foreign-actor review cannot clear the journal; a plain server business 409 does not enable arbitrary release. The existing 24-hour journal policy is unchanged and expiry is tested with a fake clock.

## QUEST-GROUP-INVITATIONS-PAGE-01

Finding key: `quest-group-invitations-next-page-20261108-0327`.

The existing recipient and manager GET contracts provide `page`/`per_page`; previously refresh always requested page one and no next-page route existed. A valid 21st invitation could not be reached from either list. Group capacity does not limit invitation history to 20; a known deep link remaining available is distinct from list reachability.

The list now uses `LazyColumn` and requests the next READ batch when its continuation enters the viewport. It preserves the group filter, actor/route context, server order and distinct IDs. Append loading/errors retain the already loaded rows and last successful page; Retry requests the same failed next page. A forbidden/unavailable append clears private rows rather than retaining inaccessible content. Empty/end lists stop requesting. Opening an older invitation and returning keeps the loaded page and list position without requesting page one again. Route/actor changes discard delayed page-two results. No write is associated with pagination.

The general manager/invitation reader and empty-list layouts are not claimed as a full visual reconciliation in this fix.
