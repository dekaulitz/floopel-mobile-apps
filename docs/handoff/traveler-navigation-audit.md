# Catalog search Back and moderation notification targets

8 November 2026. Findings **CATALOG-SEARCH-BACK-01** (`catalog-search-back-query-loss-20261108-0558`) and **NOTIF-MODERATION-TARGET-01** (`notification-canonical-moderation-target-20261108-0558`) were reported from read-only source inspection at `1fbaa17d`. The original report had no native/API reproduction; the new regression tests exercise the corrected implementation with isolated fixtures.

## Search origin state

Explorer and Spot archives previously cleared the shared query when opening a reader. Back restored queries only for location browsing. The ViewModel now retains Spot/Explorer queries in memory keyed by the complete origin route, including geographical context, and restores the matching value before requesting results. Global archives, location archives and Explorer do not borrow another origin's query. Existing scope-chip changes deliberately reapply the current query to the selected scope. Explicit clear remains clear, while identity/generation changes erase all retained searches. Search text is not added to the serialized navigation stack or persistent storage.

The change uses the existing repository/search endpoints and cancellation owner. It does not infer location from another account or a Figma example. Four host cases cover Explorer/global/scoped reader Back, independent origins, explicit clear, failed Back/retry, a cancelled late search, and identity reset. Native tests address the actual editable descendant of the shared search component and compare its exact `EditableText`, including empty text. The location case scrolls the outer Home list before selecting the location card, enters the location reader, and checks the location ID on the search request before and after Spot Back.

## Canonical owner moderation destination

The notification contract permits the exact static target `/me/itinerary-moderation`. The router now recognizes that single path in addition to its existing UUID families. External URLs, encoded paths, queries, fragments and near-match suffixes remain rejected; a null preview never becomes an authorized owner reader.

The new route loads `TravelerModerationRepository.actions()` through the existing native authorized GET `/me/itinerary-moderation-actions`. It renders the actual owner action/appeal projection with localized statuses/reason categories. Titles and itinerary IDs come from the API; reporter identity and internal notes are not projected. The pinned toolbar and read-only status composition follow the newer Android Figma frames [445:12674](https://www.figma.com/design/ifQcOxbjGTXw9aNH2JGl9g/Floopel-Mobile?node-id=445-12674), 445:12771, 445:12868, 445:12962, 445:13058, 445:13154 and 445:13250. These provide 20dp gutters, 16dp content gaps, a 24sp title, and a shared 16dp status surface with 16dp padding, 12dp gaps, 22sp status and 13sp body. Shared buttons and the mapped back icon are reused; platform status/gesture bars remain native. No new static artwork is needed.

**Buka rencana** opens the existing private itinerary reader and Back returns to the same moderation origin. **Periksa status** refreshes the GET for an existing appeal. Every notification-backed status load, including restoration, plan Back and refresh, first re-reads the exact inbox notification and checks that its current target still equals the registered static path. A different owner action is not proof of a removed/null/unsafe notification target. Failed source revalidation clears the old projection and cannot fetch owner actions or acknowledge. Existing Retry-After deadlines are respected before another read; the pacing test uses the same fake clock for the ViewModel and native session.

The notification's exact inbox ID is carried separately from itinerary/action IDs. GET/list loading alone does not acknowledge it: the root waits for a rendered frame with a nonempty, successfully authorized owner projection. Loading, empty, denied/removed, malformed or failed reads cannot acknowledge. Back/identity changes discard late reads; repeated render/refresh within the same ViewModel acknowledges once. This is not a claim of persistent deduplication across process recreation.

Eight host cases use the production notification and moderation adapters with MockEngine, including both moderation/appeal notification kinds, exact inbox PUT acknowledgement, errors/empty/invalid data, Retry-After, plan Back, late Back/identity, null/unsafe/removed targets and source reauthorization on restoration/refresh. One additional route regression locks the exact allowlist. No API, backend policy, provider configuration or live notification read state is changed.
