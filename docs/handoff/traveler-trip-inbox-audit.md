# Recipient Trip invitation pages and pending application layout

8 November 2026. Follow-up to `94a8904`, limited to **TRIP-INVITATIONS-PAGE-01** and **VD-TRIP-APP-01**. Both original reports were source findings, not reproductions against a real account or provider. Work remains on PR #1's `feature/mobile-openapi-contracts` branch.

## Recipient invitation history

The backend already accepts `cursor` (UUID) and `limit` on GET `/me/trip-invitations`. Its response is an array, with no `next_cursor` field. The old mobile port/adapter requested only the first default twenty records, so an older row could not be reached through this inbox. Records include terminal history, not just pending invitations.

`TripInvitationPage` now carries items and a locally derived continuation. The adapter sends the existing parameters, applies the backend's default twenty for limits outside 1–100, and uses the last valid row UUID only when the returned array fills the requested page. An exact full final page therefore needs one empty end read. Oversized arrays, blank/duplicate IDs, malformed last cursors and a cursor that does not advance fail closed. No response metadata, endpoint, field or backend policy is added. Optional inviter identity hydration remains per page and actor generation.

The ViewModel appends in server order with distinct IDs. Network/throttle append failure keeps the previous rows and cursor, displays a bottom retry action, and retries the same cursor. Loading and Retry-After guard duplicate More/retry calls. Initial authorization failures do not retain a readable inbox, and actor reset clears all history. A late response after Back or another actor cannot populate the current route. The organizer's separate Trip-scoped array reader remains separate.

Recipient rows use `LazyColumn` with stable invitation IDs, so loading another page does not compose all retained history at once. Row content and decision commands retain their existing behavior. Reading, More, end detection and retry never accept, decline or send an invitation. Older pending rows are actionable only while backend expiry/access checks allow the existing command; history visibility does not grant membership.

## Pending applicant

The implemented variant is exactly an **APPLICANT + PENDING + not-current-member** projection at [Figma 316:5657](https://www.figma.com/design/ifQcOxbjGTXw9aNH2JGl9g/Floopel-Mobile?node-id=316-5657). The existing toolbar title was already correct. The body now uses the compact context, centered waiting illustration, heading/body and full-width status/withdraw/catalog actions instead of the old generic status column and information card.

Figma measurements are retained: 20 dp side gutters, minimum 88 dp context with radius 16, title 15 sp and date metadata 12 sp; illustration **160 × 106.667**; feedback heading 24 sp/body 13 sp; 48 dp minimum action targets and 16 dp gaps. Feedback centers in the available space beneath the measured context. Large/long text can expand the context and scroll; native safe areas remain native.

The exact waiting SVG was downloaded into `trip_application_waiting.svg` (2,355 bytes), without changing root dimensions. There was no byte-identical existing asset. Native load and effective size are checked. The banner in Figma represents dynamic Trip imagery: a matching, previously loaded public Trip may provide its banner and organizer. Apply acknowledgement retains that context, as does opening the known application from its public reader. A direct profile/notification reader has only canonical application fields; no banner, organizer, image fallback or API field is invented. The solid-color image in one UI fixture capture is test data, not a production fallback or a Figma asset replacement.

**Periksa status** only refreshes the authorized application. Withdrawal keeps the existing confirmation and server `canWithdraw` gate; Cancel submits nothing. A new membership, terminal status, organizer or unknown viewer leaves the pending variant. **Kembali ke katalog** appears only when the immediately preceding matching Trip reader/form chain leads to an existing Open Trip catalog (including its location/query context or the Community Open Trip tab). A notification or profile detour does not borrow an earlier catalog, and toolbar Back retains the original stack. No automatic apply/withdraw or journal release is added.

High-fidelity context/screenshots for recipient confirmation [315:17683](https://www.figma.com/design/ifQcOxbjGTXw9aNH2JGl9g/Floopel-Mobile?node-id=315-17683) were also inspected as flow context. This pagination change does not claim a redesign of the recipient accept/decline confirmation pages. Existing Floopel buttons, typography/theme tokens and the mapped ArrowBack component are reused.
